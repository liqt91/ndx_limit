# 方案：单进程管理后台（类 Jenkins）

2026-10-21。与《定时触发.md》（现状）、《deploy-architecture-tick.drawio》（tick 调度表方案的
部署图）、《edgeone-迁移.md》的「L2：抓取与发信进 Cloud Functions」并列，供横向对比后再定。

一句话：**把「几点干什么、用什么凭据、跑成什么样」收进一台机器的进程里**，等价于给已经
在跑的那条 crontab 链路补上管理面。

---

## 0. 先纠正一个现状：crontab 还在跑，Node 还没装

写方案前实测了服务器（`lhins-0ky4jsqs`，上海），三条都跟文档写的不一致：

| 项 | 文档写的 | 实测 |
|---|---|---|
| 服务器 crontab | 已退役 | **仍在跑**。日志里 `2026-10-21T00:10:03Z`（= 北京 08:10）有 `broadcast.yml -> HTTP 204` |
| 服务器 Node | 面板靠它跑 | **没装**，`node -v` → none，`/usr/local/bin/node` 也没有 |
| 运维面板服务 | 已部署 | **`systemctl is-active ops-panel` → 无此 unit**，服务未安装 |

原因不难猜：EdgeOne Pages 的大陆可用区要 ICP 备案，备案没下来，所以 **EdgeOne 那条链根本没上线**，
生产调度仍然是我原来写的 crontab 两行 → `gh-dispatch.sh`（735 字节的 curl 脚本）→ GitHub Actions。

**由此带来一个你可能没注意到的现状**：crontab 只有 `07:50 refresh` 和 `08:10 broadcast` 两行，
所以今天订阅者收到的仍是**早上 08:10 那封**，下午 14:45 的报根本还没开始发。文档里写的
「订阅者每天只收 14:45 一封」是**目标态**，不是现在。

这件事直接决定方案起点：C 方案在架构上几乎没有增量——**crontab 已经在做调度了**。

## 1. 它合并了什么

现在「一个时点要跑什么」这件事被拆在四处：

| 环节 | 现在在哪 | 改一次要动几处 |
|---|---|---|
| 时间表 | 服务器 `/var/spool/cron/crontabs/root` | ssh 进去改 |
| 触发方式 | `gh-dispatch.sh`（curl GitHub API） | 改脚本 |
| 鉴权 | 服务器 `/root/.gh_dispatch_token`（P1） | 续期时还要同步 EdgeOne 那份 |
| 执行 | GitHub Actions 的 `refresh.yml` / `broadcast.yml` | 改 workflow + push |
| 观测 | Actions run 日志 + 一个没启用的面板 | 两个地方看 |

C 方案把这五行变成一行：**一个进程内的 `schedule.json`**。

## 2. 架构：一个进程，四件东西

```
                        ┌─────────────────────────────────────┐
                        │  ndx-scheduler（systemd 常驻）       │
   浏览器 ──ssh 隧道──▶ │  ┌─────────┐   ┌──────────────────┐ │
   (127.0.0.1:8780)     │  │ Web 面板 │   │ ticker（30s）     │ │
                        │  │ 调度表   │   │ 读 schedule.json  │ │
                        │  │ 历史     │   │ 到点 + 未跑 → 派发│ │
                        │  │ 重跑     │   └────────┬─────────┘ │
                        │  └────┬─────┘            │           │
                        │       │          ┌───────▼────────┐  │
                        │       └─────────▶│ runner         │  │
                        │                  │ spawn 子进程    │  │
                        │                  │ flock 串行      │  │
                        │                  └───────┬────────┘  │
                        │  状态：state.json / runs.jsonl / logs/│
                        └──────────────────────────┼───────────┘
                                                   │
              ┌────────────────────────────────────┼──────────────────────┐
              ▼                                    ▼                      ▼
      node scripts/scrape.mjs            node scripts/send.mjs       外部取数
      （本地 clone /opt/ndx_limit）        （Brevo HTTP / SMTP）
              │                                    │
              └──────────────► git commit & push ──┘
                                     │
                                     ▼
                         EdgeOne Pages 监听到 push → 重建
```

四件东西各自对应 Jenkins 的一个概念，但都简化到本项目需要的程度：

| 件 | 对应 Jenkins | 本项目的实现 |
|---|---|---|
| ticker | Timer Trigger | 每 30 秒比对一次 `HH:MM`，不做 cron 表达式解析 |
| schedule.json | Job Configuration | 一份数组，`{name, at, job, args, on}`，面板可编辑 |
| runner | Build Executor | `child_process.spawn`，`flock` 保证同 job 串行 |
| state.json / runs.jsonl | Build History | 前者是「今天这一格跑没跑」，后者是追加日志 |

**关键差别**：Jenkins 有 workspace、插件、凭据域、节点管理；这套东西一样都不要。它只需要
「到点跑一个命令、记下结果、能点重跑」。

## 3. 六个必须定死的设计点

这六条是方案的全部难度所在，其余都是 CRUD。

### 3.1 幂等：重启不能把今天跑两遍

`state.json` 的键与现在 KV 闸键同构，便于日后互换：

```json
{ "2026-10-21": { "refresh@preopen": { "runId": "r-0742-1", "at": "...", "code": 0 },
                  "refresh@intraday": { ... } } }
```

ticker 判断顺序：`到点了吗` → `今天这一格有记录吗` → 有就跳过。**状态必须落盘，不能只在内存**，
否则 systemd 重启一次当天就重跑（发信场景下这是真的会多发一封）。

### 3.2 补跑：进程宕机了怎么办

Jenkins 默认不补跑，我们的场景不行——数据必须每天有。策略要显式定：

- **过期 ≤ 120 分钟**：补跑一次（`scrape.mjs` 同日幂等，覆盖当日点，安全）
- **过期 > 120 分钟**：不自动补，面板上该格标红，等人工点「重跑」
- **发信 job 一律不自动补**：晚三小时发收盘前报不如不发；只标红 + 告警

### 3.3 并发：同一 job 不并发

用 `flock -xn /var/lock/ndx-<job>.lock`（crontab 时代验证过的方式）。
两个 refresh 撞在一起会同时写 `history.json` 再先后 push，第二个必冲突。
不同 job（refresh / broadcast）可以并行，它们不碰同一批文件。

### 3.4 时钟：显式 CST，不信系统时区

这个项目在时区上踩过一次（`new Date('...T00:00:00+08:00')` 在 UTC 机器上周一算成周日）。
所以 ticker 不读系统本地时间，而是 `Date.now() + 8h` 后取 `HH:MM`，与 `dispatch.js` 的 `cstDate()`
同源。另外 `/etc/timezone` 这次没能取到（MCP 限流），**部署第一步就把它设成 `Asia/Shanghai`**。

### 3.5 失败语义要分两类

| job | 失败后做什么 | 为什么 |
|---|---|---|
| refresh | 不写仓库、保留上次好数据、告警 | 覆盖率不达标时宁可少一天，也不要出现「今日全暂停」的假象（这条现在靠 `exit 2` 实现，要原样保留） |
| broadcast | 数据不回滚、只告警、可单独重跑 | 数据是对的，只是信没发出去 |

### 3.6 凭据：只在一处（这是本方案最大收益）

见下节。

## 4. 凭据与外部依赖

| 位置 | 留什么 | 说明 |
|---|---|---|
| 服务器 `/etc/ndx-scheduler.env`（chmod 600） | `BREVO_API_KEY`、`MAIL_FROM`、`ALERT_EMAIL`、`SUBSCRIBERS_TOKEN`、`UNSUB_SECRET`、`SITE_URL` | 全部集中，改一次生效 |
| 服务器 `/root/.ssh/id_ed25519`（deploy key） | 推仓库权限，**限单仓库、默认不过期** | 比 PAT 少一件「续期」的事 |
| EdgeOne | `SUBS_KV`、`BREVO_API_KEY`、`SUBSCRIBERS_TOKEN` | 只剩订阅三函数（subscribe / confirm / unsubscribe） |
| GitHub | **零 secret** | 两个 workflow 与全部 secrets 可删 |

对比现在：GitHub Secrets 8 项 + EdgeOne env 6 项 + 服务器 3 份凭据文件。
对比 tick / L2-A：那两条路都还留着「EdgeOne 一个 PAT + 服务器一个 CRON_SECRET」的一对。

**但有一条未验证**：deploy key 走 SSH 22。大陆到 `github.com:22` 经常被限速或不通，
而这次 `execute_command` 被 MCP 限流了，没测成。**这是本方案的前置条件**——不通就只能退回
HTTPS + fine-grained PAT（那凭据又变成一份 PAT，收益打折）。

## 5. 单点与恢复（本方案最弱的一处）

**单点**：这台机器停 → 数据停、发信停。订阅入口仍在 EdgeOne（用户还能提交），只是没人处理。

**自愈**：`Restart=always`、`RestartSec=5`、开机自启，再加 3.2 的补跑窗口。

**★ 一个必须承认的硬缺口：没有外部视角。** 面板和调度在同一台机器上，机器挂了的时候，
「面板打不开」和「网络不通」你分不出来，而且没人通知你。补救办法只有一条：

> 暴露一个只读端点 `GET /api/heartbeat?t=<token>`，返回
> `{"ok":true,"lastRunAt":"...","nextAt":"..."}`，由**外部**每天探一次
> （GitHub Actions 一个 10 行的 workflow，或任何 Uptime 服务，10 秒的事）。
> 连续两次 5xx 或超时就发邮件。

这条不补，C 方案就等于放弃了「出问题会告诉你」这个能力——而现在 EdgeOne 的 dispatch 是有
失败告警邮件的。

**备份**：`schedule.json`、`state.json`、`runs.jsonl` 三个文件，每天 rsync 到本地或另一台机器。
`schedule.json` 建议同时提交进仓库一份，这样「调度表被谁改过」有 git 记录。

## 6. 迁移步骤（每步都有回滚点）

前提：**现在生产是 crontab 在跑，所以任何一步都不能让它停**，除非新链路已经验证过同一时点。

1. **装 Node 22 + 设时区**，`git clone` 到 `/opt/ndx_limit`。判据：`node -v` 有输出、
   `date` 显示 CST、`node scripts/scrape.mjs --dry` 能跑（不写仓库）。
2. **装 systemd unit，调度开关默认 off**。只启面板（听 127.0.0.1:8780，与现在同步）。
   判据：ssh 隧道打开能看到页面，`schedule.json` 全部 `on:false`。
3. **手动触发一次 refresh**（面板按钮），比对产出与 Actions 那份 `data/*.json` 是否一致
   （字段、条数、覆盖率）。判据：`git diff` 只有时间戳类差异。
4. **挑一个时点切换**。顺序不能反：先在本机把 `on` 打开到「下一跳」，等它真跑成功并 push，
   **再从 crontab 里删掉对应那行**。中间那个时点允许双跑一次 refresh（幂等，无害），
   但**绝不允许 broadcast 双跑**——所以 broadcast 的切换必须放在 07:50 之后、次日 08:10 之前完成。
5. **验证三件事**：push 是否触发 Pages 构建；面板历史里有 runId 和退出码；告警邮件能发到。
6. **观察 3 天**，再把 EdgeOne 的 `dispatch` / `status` 删掉（面板不再需要 status 投影）。
7. **回滚**：`crontab -e` 加回两行 + `systemctl stop ndx-scheduler`，两分钟。

## 7. 四个方案横向对比

| 维度 | 现状（crontab + Actions） | tick（调度表进 KV） | L2-A（执行进 Cloud Fn） | **C（单进程后台）** |
|---|---|---|---|---|
| 改抓取时刻 | ssh 改 crontab | **面板改一行** | 面板改一行 | **面板改一行** |
| 前置条件 | 无 | EdgeOne 上线（要备案） | EdgeOne 上线 | **无，现在就能用** |
| 凭据份数 | 4 份 / 3 类 | 4 份 | 2 份 | **1 处**（deploy key 不过期） |
| 调度单点 | 服务器 | EdgeOne | EdgeOne | 服务器 |
| 执行单点 | GitHub | GitHub | EdgeOne | 服务器 |
| 失败告警 | Actions 邮件 + dispatch 告警 | 同左 | EdgeOne 侧发 | 自己做（面板 + 心跳探活） |
| 重跑 | GitHub 一键 Re-run | 同左 | 要自己做 | 面板按钮（天然） |
| 日志 | **Actions 完整日志** | 同左 | EdgeOne 日志分析（24h 窗口） | 本地文件（可 grep、可留久） |
| 匿名攻击面 | crontab 不暴露 | 只剩 tick（无参数） | 只剩函数入口 | **无**（只听回环） |
| 额外运维 | 无 | 无 | 无 | systemd + 日志轮转 + 备份 + 探活 |
| 与当前 WIP 冲突 | — | 无 | **碰 scrape/digest** | **碰 scrape/send/git 写入部** |
| 迁移风险 | — | 低（执行层不动） | 中 | **中高**（换执行环境，要重验数据一致性） |

一个容易被忽略的观察：**C 和现状在「单点」上其实是同一件事**——现在调度就在服务器上。
C 只是把 crontab 换成有界面的进程，并没有新增一个单点。真正的单点变化是
「从今天起，执行也不再依赖 GitHub」。

## 8. 什么时候该选它，什么时候别选

**该选**：

- 你本来就打算长期留这台机器（面板也在上面），多一个常驻进程的边际成本很低。
- **你想让「改代码 → 试跑」变快**。这是 Actions 最难受的地方：改一行 `scrape.mjs`，
  要 push → 等 workflow → 看日志，一轮三五分钟；在本机上 `node scripts/scrape.mjs` 就是真环境。
  抓取逻辑还在频繁变（你这轮 `scrape.mjs` 就改了 254 行），这条价值不小。
- 你更愿意相信 `ssh` 和文件，而不是三个控制台。

**别选**：

- 你希望「服务器哪天停了，站还在、数据还在更新」——这条只有 EdgeOne / Actions 能给。
- 你不想管 systemd、日志轮转、磁盘、备份、探活这套东西（这是真实存在的长期负担）。
- 你的抓取逻辑快稳定了，一年改不到几次——那「改代码试跑快」这个收益就不值它的运维成本。

**一个必须知道的反向风险**：代码在服务器上跑意味着它跑的是仓库 `main` 的一份副本。
每次运行前要 `git fetch && git reset --hard origin/main`，否则会跑旧代码；反过来，你 push 了
坏代码，下一次服务器运行就中招（Actions 也一样，但 Actions 至少能在 diff 里看出来）。

## 9. 折中版：C-lite（可能才是你真正想要的）

如果你要的只是「别再 ssh 改 crontab、能看到跑成什么样、能点重跑」，可以只做最小的一层：

**不搬执行，只把现在 crontab 的两行包进后台**——进程仍然只调 GitHub API，服务器仍然不装 Node、
不 clone 仓库。

| | C-lite | 完整 C |
|---|---|---|
| 装 Node / clone 仓库 | 不需要 | 需要 |
| 改调度时刻 | 面板 | 面板 |
| 跑历史 / 重跑 / 审计 | 有 | 有 |
| 凭据 | 不变（服务器仍持一份 PAT） | 收敛到一处 |
| 与 WIP 冲突 | **无** | 会碰 scrape / send |
| 工作量级 | 在现有 883 行面板上加两个页面 | 加调度器、执行器、状态机 |

**C-lite 和 tick 的区别只有一个：调度表存哪。** tick 存 EdgeOne KV（要备案下来才能用），
C-lite 存本机文件（今天就能用）。功能几乎一样，依赖完全不同。

如果备案还要等一段时间，C-lite 是这段时间里唯一能立刻改善体验的做法。

## 10. 待验证（动手前必须清掉）

1. **服务器 → `github.com:22` 是否通**（deploy key 的前提）。MCP 限流没测成。
   退路：HTTPS + fine-grained PAT，或 SSH over 443（`ssh.github.com:443`）。
2. 服务器 → `github.com` 的 HTTPS git 协议（clone / push over 443）。
3. 服务器时区是否 `Asia/Shanghai`（`/etc/timezone` 未取到）。
4. `scrape.mjs` 在服务器上跑一次的耗时（本地基线 15 秒；服务器爬东财实测 0.11s/请求，
   理论上更快，但要实测 56 只的并发表现）。
5. systemd unit 与端口 8780 是否被占。
6. 若 C 落地，EdgeOne 的 `dispatch` / `status` 删除后，面板要改数据源（现在 EO 优先、
   本地日志降级，删了之后只剩本地，降级逻辑可以简化成唯一路径）。

---

## 11. 结论

- 论「少一个平台」，C 方案是四个里最彻底的：**调度、执行、观测、凭据全在一处**，匿名攻击面归零。
- 论「少一件事要维护」，它是最差的：多一个常驻进程、一份日志、一份备份、一个探活。
- 它并不新增单点（调度本来就在这台机器上），但**它把执行也压到这台机器上**，于是
  「机器挂了站还在」这个属性消失了。
- 所以真正的取舍不是技术，是**你更怕哪种故障**：怕「改了不知道跑没跑」→ 选 C；
  怕「机器挂了数据就停」→ 留 EdgeOne / Actions。

如果只想立刻止痛、不想承担执行层迁移，**先做 C-lite**。
