# 定时触发：EdgeOne schedules → GitHub Actions

## 背景

GitHub Actions 自带的 `schedule` 是**尽力而为**，不保证准点。UTC 00:00 是全球最拥挤的时段，
官方文档明确建议避开整点。实测（2026-10-20）：计划 UTC 00:00（北京 08:00），实际 02:44 UTC
才启动，**晚 2h44m**；当天 `Daily Broadcast`（计划 UTC 00:20）甚至到 03:35 UTC 仍未被调起。

延迟会造成两个后果：

1. 发信门禁（`check-freshness.mjs`）发现「数据不是今天的」→ 变红拒发，邮件丢失；
2. 若再引入另一个外部触发器，会和 GitHub 自带调度**双跑**，broadcast 会重复给订阅者发邮件。

演进（两代外部触发，workflow 侧始终只保留 `workflow_dispatch`）：

1. **第一代（2026-10-20 ~ 10-21）**：轻量云 crontab → `gh-dispatch.sh` → GitHub dispatch
   接口。时间精确，但链路里有一台服务器和一枚一年期的 PAT。
2. **第二代 L1（2026-10-21 落地）**：**EdgeOne `edgeone.json` 的 `schedules`**（北京
   07:50 / 08:10，`Asia/Shanghai`）→ POST `/api/jobs/dispatch`（Edge Function）→ GitHub
   dispatch。零服务器，dispatch 失败发告警邮件到站长邮箱。架构、安全模型、部署与回滚
   详见 **《edgeone-迁移.md》**；crontab 两行已退役（见下）。

> 双跑风险仍在：**EdgeOne schedule 与服务器 crontab 不能同时开**——两者都会 dispatch
> broadcast，订阅者会收到两遍日报。切换时必须先删 crontab 再加 schedule（或反之）。

## 触发脚本 `/usr/local/bin/gh-dispatch.sh`

**单一来源在仓库 `scripts/ops-panel/gh-dispatch.sh`**（2026-10-21 起；服务器上的是部署副本，
crontab 与运维面板都调用服务器这一份）。较本文档早期内联版本有三处变化：

- 新增可选第二参数：`gh-dispatch.sh broadcast dry` → `mode=dry-run`（只打印不发信）；
  不带第二参数仍是 `mode=send`，crontab 现有写法不受影响；
- 非 204 时退出码为 1（以前静默返回 0），cron 与面板都能据此判断失败；
- 缺 token 时退出码为 3。

用法：`refresh`（安全）/ `broadcast`（真发信）/ `broadcast dry`（dry-run）。
凭据、crontab、验证与下文相同。重新部署步骤见《管理面板.md》。

## 定时任务（crontab，root）——已退役，保留作回滚用

L1（2026-10-21）起主触发是 EdgeOne schedules，**服务器 crontab 两行已删**（不删会与
schedule 双跑、broadcast 发两遍）。回滚时把下面两行加回 `crontab -e` 即可，一分钟：

```cron
CRON_TZ=Asia/Shanghai
50 7 * * * /usr/local/bin/gh-dispatch.sh refresh  >> /var/log/gh-dispatch.log 2>&1
10 8 * * * /usr/local/bin/gh-dispatch.sh broadcast >> /var/log/gh-dispatch.log 2>&1
```

> 服务器自带的 `*/5 * * * * ... stargate ... start.sh` 是腾讯轻量云监控 agent，勿动。

## Token

- 文件 `/root/.gh_dispatch_token`，`chmod 600`，**绝不进仓库**
- 类型：GitHub **细粒度 PAT**（Fine-grained token）
- 权限范围：仅授权仓库 `liqt91/ndx_limit`，Repository permissions → **Actions = Read and write**
- 过期设长一些（≥1 年）；到期前需重新生成并覆盖该文件
- 续期时顺手把 `{"issuedAt":"...","expiresAt":"..."}` 写进 `/root/.gh_dispatch_token.meta.json`，
  运维面板会显示剩余天数（见《管理面板.md》）
- ★ **L1 起 PAT 有两处副本**：服务器文件 + EdgeOne 控制台环境变量 `GH_DISPATCH_TOKEN`。
  续期必须同步更新，漏一处的表现是「一半触发失败、告警邮件说 401」。

## Workflow 侧

`refresh.yml` / `broadcast.yml` 均已**删除 `schedule:`，只保留 `workflow_dispatch`**，避免与外部
cron 双跑重复发信。手动兜底仍在：GitHub 仓库 Actions 页面可点 `Run workflow` 触发。

## 验证

- **主路径（L1）**：EdgeOne 控制台 → 日志分析，应每天两行
  `[dispatch] refresh → refresh.yml HTTP 204` / `[dispatch] broadcast → broadcast.yml HTTP 204`；
  KV 里出现当日 `job_sent_refresh_<日期>` / `job_sent_broadcast_<日期>`。
  失败时站长邮箱会收到《【ndx】dispatch 失败》告警信（Brevo，Server酱/飞书未开通）。
- 冒烟测试（代码级）：`npm run jobs:smoke`（65 断言，零外网）。
- **兜底路径（服务器/面板）**：`tail -f /var/log/gh-dispatch.log`，手动
  `/usr/local/bin/gh-dispatch.sh refresh`（安全，不发邮件，期望 204）。
- 2026-10-20 13:18 实测 crontab 版 `refresh -> HTTP 204`，链路闭环；`broadcast` 首封日报于次日 08:10 实弹验证

## 故障排查

- **某天没收到日报**：先看站长邮箱有没有《【ndx】dispatch 失败》告警信 + EdgeOne 日志分析
  里有没有 204 行。有告警 → 按信里提示处理（多为 PAT 过期或出口不通）；没告警也没 204 →
  看 schedule 是否注册成功（《edgeone-迁移.md》待验证项 1）。任何情况下都能用
  GitHub Actions 页面手动 `Run workflow` 兜底。
- **token 过期**：重新生成细粒度 PAT（仍只授权本仓库 Actions 读写），**同步两处**：
  服务器 `/root/.gh_dispatch_token`（保持 `chmod 600`）+ EdgeOne 控制台 `GH_DISPATCH_TOKEN`。
- **脚本/crontab 丢失**：按上文重新粘贴安装即可；workflow 侧无需再改。

## 已知缺口与已否决方案（2026-10-21 盘点）

盘点「这条链路怎么管理」时确认的事项，留档防重复讨论：

1. **dispatch 层失败无推送（L1 已关闭，2026-10-21）**：现在由
   `edge-functions/api/jobs/dispatch.js` 在 GitHub 非 204 / 网络异常时发 Brevo 告警邮件
   到 `ALERT_EMAIL`，401 会明确提示「PAT 过期，同步更新服务器与控制台两处」。
   面板侧还聚合 `/api/jobs/status`（KV 事件流水）看见这一跳的每次终态。
   仍只剩 GitHub 邮件覆盖的是 workflow 内部失败（门禁拒写、发信失败）——L2 把活搬进
   函数后这层才由函数自己告警。
2. **PAT 到期无提醒**：有效期 1 年，到期即静默失败。修法：日历提醒（提前两周）+
   边缘函数识别 401 给出明确报错（已随 L1 落地）。换 GitHub App installation token 可自动轮换，
   但要多一套 JWT 签发，为一天一次的调用不划算，不做。
3. **gh-dispatch.sh 单一来源（2026-10-21 已落地）**：脚本进仓库
   `scripts/ops-panel/gh-dispatch.sh`，服务器 `/usr/local/bin/` 下为部署副本；
   运维面板复用同一脚本，cron 与面板走同一 dispatch 实现。变更时两边同步，
   部署步骤见《管理面板.md》。
4. **公网 web 控制台：已评估并否决**。理由不变：触发是低频写操作，公网端点要认真做鉴权。
   但「集中管理位」的诉求用**内网页面板**满足（2026-10-21 落地）：只听 `127.0.0.1`、
   SSH 隧道访问、broadcast 真发信二次确认、触发写审计日志。部署与访问见
   `docs/ops/管理面板.md`，代码在仓库 `scripts/ops-panel/`。
5. **Lighthouse → SCF 迁移：已 supersede**。主触发不再需要服务器（L1 起走 EdgeOne
   schedules）；轻量云现在只为运维面板存在。若面板也找到去处（token 保护的云函数，或
   砍掉用日志分析 + 告警邮件代替），服务器即可退役，省续费（2027-10-15 前决策）。
   SCF 出口可达性不再需要验证。
