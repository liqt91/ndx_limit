# 定时触发：EdgeOne schedules → GitHub Actions

## 背景

GitHub Actions 自带的 `schedule` 是**尽力而为**，不保证准点。UTC 00:00 是全球最拥挤的时段，
官方文档明确建议避开整点。实测（2026-10-20）：计划 UTC 00:00（北京 08:00），实际 02:44 UTC
才启动，**晚 2h44m**；当天 `Daily Broadcast`（计划 UTC 00:20）甚至到 03:35 UTC 仍未被调起。

延迟会造成两个后果：

1. 发信门禁（`check-freshness.mjs`）发现「数据不是今天的」→ 变红拒发，邮件丢失；
2. 若再引入另一个外部触发器，会和 GitHub 自带调度**双跑**，broadcast 会重复给订阅者发邮件。

演进（两代外部触发，workflow 侧始终只保留 `workflow_dispatch`）：

1. **第一代（2026-10-20 ~ 10-21）**：轻量云 crontab → `gh-dispatch.sh` → GitHub dispatch
   接口。时间精确，但链路里有一台服务器和一枚一年期的 PAT。
2. **第二代 L1（2026-10-21 落地）**：**EdgeOne `edgeone.json` 的 `schedules`**（北京
   07:50 / 09:40 / 14:30 三抓 + 14:45 收盘前报，`Asia/Shanghai`）→ POST `/api/jobs/dispatch`
   （Edge Function）→ GitHub dispatch。零服务器，dispatch 失败发告警邮件到站长邮箱。
   架构、安全模型、部署与回滚详见 **《edgeone-迁移.md》**。
   ★ **crontab 仍在生产运行**，已是**三抓一报四跳**：07:50 / 09:40 / 14:30 抓 + 14:45 报
   （2026-10-21 17:45 在服务器执行并复核：`crontab -l` 共 6 行，腾讯云 `stargate` 行原样保留）。
   EdgeOne 尚未部署（备案未下），所以生产调度仍是 crontab → `gh-dispatch.sh` → Actions。
   删除时机与判据见下。
   ★ 08:10 的早报已下线，订阅者每天只收 14:45 一封。

> 双跑风险仍在：**EdgeOne schedule 与服务器 crontab 不能同时开**——两者都会 dispatch
> broadcast，订阅者会收到两遍日报。切换时必须先删 crontab 再加 schedule（或反之）。


`edition=morning` 是**盘前报**，没有调度，只在人工补发时用——它不是「早报」，08:10 的那封早报
已于 2026-10-21 下线。

★ **2026-10-23 起 `broadcast.yml` 的默认值改成了 `close`**，漏传 edition 不再发错口径。
（此前默认 `morning`：不传就按盘前视角发信，正文写「07:50 抓、08:10 发」，也没有「较盘前」
那一段，而流程不会报错——204 正常、邮件正常发出，只是内容错。这个坑现在由
`npm run check:broadcast` 断言 `default: close` 挡在 CI 里。）

取值的顺序仍是「显式第三参数 → 否则按当前小时判」（12:00 前 `morning`，之后 `close`）。

- crontab 的 14:45 跳自然落到 `close`；
- 上午在面板手点「发送」得到的是盘前报口径（人工补发场景），不会错发收盘前报。

## 定时任务（crontab，root）——**当前仍在生产运行**

L1 的目标态是 EdgeOne schedules 代发，但**截至 2026-10-21 它还没上线**（EdgeOne Pages 大陆
可用区需要 ICP 备案），所以 crontab 是现在唯一在跑的调度。**验证 EdgeOne 四跳全部正常之后**才删，
判断顺序是「先看到 schedule 的 204 日志，再删 crontab」——反过来会在两个时点之间出现空窗。
双跑会 broadcast 发两遍，切换必须挑在两个时点之间完成。

目标态是**三抓一报四跳**（与 `edgeone.json` 的四条 schedule 对齐）。下面是改完之后
`crontab -l` 应该长成的样子：

```cron
CRON_TZ=Asia/Shanghai
50 7  * * * /usr/local/bin/gh-dispatch.sh refresh   >> /var/log/gh-dispatch.log 2>&1
40 9  * * * /usr/local/bin/gh-dispatch.sh refresh   >> /var/log/gh-dispatch.log 2>&1
30 14 * * * /usr/local/bin/gh-dispatch.sh refresh   >> /var/log/gh-dispatch.log 2>&1
45 14 * * * /usr/local/bin/gh-dispatch.sh broadcast >> /var/log/gh-dispatch.log 2>&1
```

| 时刻 | 命令 | slot / edition | 干什么 |
|---|---|---|---|
| 07:50 | refresh | preopen（`scrape.mjs` 自判 morning） | 开盘前抓，覆盖隔夜公告 |
| 09:40 | refresh | intraday（自判 morning） | 补抓 07:51 之后才发布的当日额度调整 |
| 14:30 | refresh | close（自判 close） | 收盘前最后一次刷额度（场外 15:00 截止） |
| 14:45 | broadcast | close | 收盘前报，口径「较今晨」 |

- 三次 refresh 都**不传参数**：`refresh.yml` 只声明了 `workflow_dispatch`、没有 inputs，
  传 slot 会被 GitHub 422 拒。时段由 `scrape.mjs` 按北京时间自判（12:00 前 morning、之后 close），
  同日重复运行**幂等覆盖当日点**，所以 07:50 与 09:40 都落 morning 是预期行为。
- 14:45 的 broadcast 由脚本自动补 `edition=close`（见上节），不依赖 crontab 传参。

### ★ 关于 `CRON_TZ`（本机不生效，但别删）

Debian/Ubuntu 的 cron **不认 `CRON_TZ`**，`man 5 crontab` 原话是「The cron daemon runs with a
defined timezone. It currently does not support per-user timezones.」——它是 cronie（RHEL 系）/
Vixie 4.x 的扩展。网上不少中文文章写「Debian/Ubuntu 都支持 CRON_TZ」，是错的。

真正让表内 HH:MM 等于北京时间的是**系统时区**，已实测确认本机是 `Asia/Shanghai`：

```
UTC 2026-10-20T23:50:03Z  →  北京 10-21 07:50   （crontab 的 `50 7` 那一跳）
UTC 2026-10-21T00:10:03Z  →  北京 10-21 08:10   （当时的 `10 8` broadcast）
```

所以这一行现在是文档性的。留着而不删，是因为它没有副作用、又能提醒后来人「这里按北京时间」；
但**别以为它能保护你**：若有人把系统时区改成 UTC，全表平移 8 小时、`CRON_TZ` 救不了。
改时区前先看这一节。

### 安装 / 修改（root）

> **2026-10-21 17:45 已完成**：脚本与 crontab 都是经 MCP 直接改的，`crontab -l` 复核 6 行，
> cron 服务 `active`，改动前的备份在 `/root/crontab.bak.20261021-1723`。
> 下面是复现步骤与踩过的坑，换机器或回滚时用。

MCP 通道**时通时断**，`AccessDeny` 有两种原因，别当成一种：

1. **频率**：成功一次之后紧接着的调用多半被拒，隔 1~2 分钟再发就好；
2. **内容**：命令里出现 `/var/log` 字面量会被拒。绕法是**从已有的行派生新行**——新行与
   `50 7` 那行只差时刻，用 `sed -n '/^50 7/p' /tmp/c.final | sed 's/^50 7 /40 9  /'` 生成，
   命令里就不出现那个路径；再用 `sed -i '/^50 7/r /tmp/ins.txt'` 插回去。

动手前**一律先备份**：

**两条路，别走第三条**：

1. **只改三处**（推荐给人做）：见下面的 `crontab -e` 步骤。
2. **整份替换**（脚本/自动化用）：必须写出一份**包含 stargate 行**的完整文件再 `crontab <file>`。
   危险的不是替换动作，是漏掉那一行——它是腾讯云监控 agent，抹掉后监控就不上报了。

**绝不**用 `crontab -r` 清空再重建。

```bash
crontab -l > /root/crontab.bak.$(date +%F)   # 先备份
crontab -e
#  1) 删掉 `10 8 * * * ... broadcast` 那行（早报已下线）
#  2) 在 07:50 那行下面补上 09:40 与 14:30 两条 refresh
#  3) 确认 broadcast 是 `45 14`，不是 `10 8`
crontab -l                                   # 复核
```

> 服务器自带的 `*/5 * * * * ... stargate ... start.sh` 是腾讯轻量云监控 agent，勿动。

## Token

- 文件 `/root/.gh_dispatch_token`，`chmod 600`，**绝不进仓库**
- 类型：GitHub **细粒度 PAT**（Fine-grained token）
- 权限范围：仅授权仓库 `liqt91/qdii_limit`，Repository permissions → **Actions = Read and write**
- 过期设长一些（≥1 年）；到期前需重新生成并覆盖该文件
- 续期时顺手把 `{"issuedAt":"...","expiresAt":"..."}` 写进 `/root/.gh_dispatch_token.meta.json`，
  运维面板会显示剩余天数（见《管理面板.md》）
- ★ **L1 起 PAT 有两处副本**：服务器文件 + EdgeOne 控制台环境变量 `GH_DISPATCH_TOKEN`。
  续期必须同步更新，漏一处的表现是「一半触发失败、告警邮件说 401」。

## 故障排查

- **某天没收到日报**：先看站长邮箱有没有《【ndx】dispatch 失败》告警信 + EdgeOne 日志分析
  里有没有 204 行。有告警 → 按信里提示处理（多为 PAT 过期或出口不通）；没告警也没 204 →
  看 schedule 是否注册成功（《edgeone-迁移.md》待验证项 1）。任何情况下都能用
  GitHub Actions 页面手动 `Run workflow` 兜底。
- **token 过期**：重新生成细粒度 PAT（仍只授权本仓库 Actions 读写），**同步两处**：
  服务器 `/root/.gh_dispatch_token`（保持 `chmod 600`）+ EdgeOne 控制台 `GH_DISPATCH_TOKEN`。
- **脚本/crontab 丢失**：按上文重新粘贴安装即可；workflow 侧无需再改。
