# 基金列表排序逻辑 · 方案

- 状态：设计稿，待实施
- 日期：2026-10-21
- 影响页面：首页（人民币 / 美元两节）、我的基金
- 不影响：交易日历页、每日快照（按日期倒序，本就无语义问题）、基金详情页（单份额）
- 前置约定：`src/lib/status.ts` 的 `classRank`（族内份额次序 A→C→D→E→F）不动，本方案只管**族（卡片）与族之间的次序**

---

## 0. 一句话

卡片顺序从「`funds.json` 的人工录入顺序」改为**一条确定的比较链**：
先按「今天能不能买」分区，可买家族内部按「额度强度」降序，
同强度按公司名（码位序）与最小份额代码兜底——保证任何输入顺序渲染结果完全一致。

排序要回答的是读者扫屏幕时的第一个问题：**今天哪只买得到、能买多少。**

## 1. 现状与问题

当前顺序 = `funds.json` 里条目的录入顺序（`loader.ts` 的 `assemble()` 原样 push，
`index.astro` / `my.astro` 只对族内份额做了 `classRank`）。三个具体问题：

1. **首屏与列表自相矛盾。** 首屏说「今天 8 家开门，150 元可投」，
   下面第一张卡可能是一家暂停基金——读者要自己从 17 张卡里数出那 8 家。
2. **顺序无原则、不可预期。** 录入顺序既非拼音也非规模（天弘出现两次，D 类一条、
   A/C 一条，中间还隔着别家）；新增一只基金时「放哪」没有答案，全凭手感。
3. **顺序是隐藏的手工状态。** 改 `funds.json` 的顺序会静默改变全站页面，
   而这件事没有任何地方记录过。

## 2. 排序主轴：三个候选与取舍

| 候选 | 规则 | 判断 |
|---|---|---|
| A. 公司名固定序 | 现状的思路延伸，按公司排 | **否**。稳定，但把「可买的」埋进中段，首屏结论与列表脱节（见 1.1） |
| B. 限额升序 | 「10 元党」顶最前 | **否**。与首屏「150 元可投」的口径相反，且读者问的是「能买多少」不是「门槛多低」 |
| C. **额度强度降序**（采纳） | 可买在前，族内按当日额度强度从大到小 | 与首屏总数、热力图色阶（`LIMIT_STOPS`）同一口径；页面读起来就是一张「今日额度榜」 |

代价说清楚：**顺序会随额度天天变**。这是特性不是 bug——额度变化日本来就要重读列表，
「今日变化」清单和 21 天热力图已经负责回答「什么在变」，榜单负责回答「今天买什么」。
若日后想要稳定序，见 §6 的 BACKLOG。

## 3. 完整排序规则

### 3.1 分区

| 分区 | 内容 | 位次 |
|---|---|---|
| 可买 | 族内任一份额为 `OPEN` / `LIMITED` | 0（最前） |
| 不可买 | 全族 `STOPPED` / `CLOSED` / `UNKNOWN` | 1 |

美元份额本来就在独立小节（「美元基金」），**不与人民币混排、不与人民币额度相加**；
小节内部用同一条比较链（§3.2），总额度按美元计。

### 3.2 比较链（可买分区）

| # | 键 | 方向 | 说明 |
|---|---|---|---|
| 1 | `quotaKey` 降序 | ↓ | 族内有 `OPEN`（无限额）份额 → `Infinity`；否则 = 当日可买份额**已知**上限之和。`OPEN` 语义上支配任何有限额，必须压在一切限额家族之前 |
| 2 | `hasMissing` 升序 | ↑ | 「含待核验额度」（`limitMissing`）的家族下沉到可买分区末尾。**待核验不参与数值比较**——猜一个数进去比不排更糟；但也不与暂停混，它们仍可能可买 |
| 3 | 可买份额数 降序 | ↓ | 同额度下类别多的家族选择更多 |
| 4 | 公司名 升序（码位序） | ↑ | `a < b` 的 UTF-16 码位比较，**不用 `localeCompare`**：后者的中文排序结果随 ICU 数据版本变化，CI 与本地构建会产出不同 HTML，静态站每日重建的 diff 会因此抖动 |
| 5 | 族内最小份额代码 升序 | ↑ | 数值比较。到此必然全序（代码唯一），不依赖 `Array.sort` 的稳定性 |

### 3.3 比较链（不可买分区）

| # | 键 | 方向 | 说明 |
|---|---|---|---|
| 1 | 状态严重度 升序 | ↑ | `UNKNOWN`(0) → `CLOSED`(1) → `STOPPED`(2)。未公布只是没抓到、不是不能买，离「可买」最近排最前；封闭期已知重开日，排暂停前 |
| 2 | 公司名 升序（码位序） | ↑ | 同 §3.2-4 |
| 3 | 族内最小份额代码 升序 | ↑ | 同 §3.2-5 |

### 3.4 族内份额次序

沿用现有 `classRank`：A → C → D → E → F → 其它，同类别按代码。不动。

### 3.5 已知边界

- **全部暂停日**：单分区，退化成公司序。符合预期。
- **待核验家族**：位次规则见 §3.2-2；卡片上的 `≈` 与「含待核验额度」标注已存在，排序不制造新信息也不掩盖旧信息。
- **数据过期（stale）**：排序照用最新数据日，与首屏口径一致；过期提示由现有机制管，排序不掺和。
- **新增基金/份额**：加入 `funds.json` 即落位，不需要维护任何顺序文件——这正是本方案要消灭的手工状态。

## 4. 落地方式

新增 `src/lib/family-sort.ts`（纯函数，无 IO）：

```ts
export interface FamilyGroup { currency: string; shares: FundShare[] }
/** 族内份额键：A→C→D→E→F（复用 status.ts 的 classRank） */
export function quotaKey(g: FamilyGroup): number;      // OPEN → Infinity
export function compareFamilies(a: FamilyGroup, b: FamilyGroup): number;
export function sortFamilyGroups(groups: FamilyGroup[]): FamilyGroup[];
```

- `index.astro`：`cny` 与 `usdGroups` 各过一次 `sortFamilyGroups`。
- `my.astro`：`groups` 同样过一次。该页是「本地持有过滤」，过滤后相对顺序即本方案顺序，无需额外逻辑。
- `loader.ts` 的 `assemble()` 不动（它只管装配，不管呈现次序）。
- 分组键建议加上 `indexKey`（现为 `company|baseName|currency`）：站点日后收录标普500时排序链天然兼容，现在加上是零成本的。

## 5. 验收口径与负向验证

判据脚本**进仓库**（建议 `scripts/verify-family-sort.mjs`，可挂 `ci:build` 前），
不留在 `/d/tmp`——博客项目的教训是临时脚本会静默消失，门禁跟着失效。

正向（渲染层，保用）：

1. 首页人民币小节第一张卡 = 当天 `quotaKey` 最大的可买家族（等值断言，不是「前 N 张里有」）。
2. 全部可买家族位列全部不可买家族之前（按卡片顺序扫描，找到第一个不可买卡后不允许再出现可买卡）。
3. 卡片总数 = 分组总数（按当天数据实况，不得因排序丢卡/重复卡）。
4. `npm run build` 后既有断言全绿（`verify-nav-align.cjs` 等）。

负向（注入破坏，证明门禁有牙）：

5. 打乱 `funds.json` 条目顺序 → 渲染卡片顺序逐字节一致（证明不依赖录入顺序、比较链是全序）。
6. 注入「只按公司名排序」→ 断言 1、2 必须红（证明判据真的在看额度分区）。
7. 注入「删掉最小代码兜底」→ 构造两只同键家族，两次不同输入顺序输出不同 → 证明兜底必要（顺带证明它不是死代码）。
8. 注入 `localeCompare` 版本 → 在含中文公司名的 fixture 上顺序与码位序不同则红（锁死 §3.2-4 的环境依赖问题）。

## 6. 不做的事（登记 BACKLOG）

- **客户端交互排序**（点列头切换升降序）：纸感列表没有列头可点；17 张卡一屏放得下，静态站无需为此引 JS。
- **按近 7 日开门天数排序**：引入第二个时间口径，读者要心算；抓取历史不足 7 天时还会静默降级。弊大于利。
- **直销额度进排序键**：`channelHighlight` 是渠道差异不是额度差异，排序主轴混入它会同时搞乱「今天能买多少」这一个问题。卡片上已有的直销标注足够。
